# ユーザーマニュアル作成

`docs/manual/` の HCOSS ユーザーマニュアルを執筆・更新する。読者は業務担当者（販売・製造・パート・経営者）であり、開発者ではない。

このマニュアルの価値は網羅性ではなく **「画面の前に座った担当者がその場で手を動かせること」** にある。だから節の構成は「何ができるか → どこを開くか → 何が表示されるか → どう操作するか → 気をつけること」の順に固定されている。この順序は読者が実際に迷う順序であり、崩すと読者は自分の状況に対応する記述を探せなくなる。

## 全体構成

```text
docs/manual/
├── index.md                      # 構成・執筆テンプレート・キャプチャ方針（マニュアルのメタ文書）
├── 00-はじめに.md                 # 読み方・表記規約・動作環境
├── 01-業務フロー.md               # WF-1〜WF-6 の全体像（各章への入口）
├── 02-共通操作.md 〜 08-返品処理.md  # 画面別の操作章
├── 用語集.md                      # 付録 A
├── 付録B-トラブルシューティング.md  # 付録 B（Q&A 形式）
└── assets/*.png                  # 画面キャプチャ（Playwright が自動生成）
```

章はメニュー構成（ホーム／受注／在庫／商品／出荷）に沿って並べる。章番号は画面の並び順であって業務の順序ではない。業務の順序は第 1 章の業務フローが担い、各章はそこから参照される。

## 節の執筆テンプレート

画面・タブごとに 1 節を立て、次の構成で書く。

```markdown
## <章.節> <画面・機能名>

### この画面でできること

- （業務上の目的を 1〜3 行。「何のためにこの画面を開くか」を書く）

### 画面の開き方

- メニュー「<トップ>」→ タブ「<タブ名>」（URL: `/xxx?tab=yyy`）

### 画面の説明

![<画面名>](assets/<章番号>-<slug>.png)

| # | 項目 | 説明 |
|---|------|------|
| ① | <UI 要素> | <役割> |

### 操作手順

1. （番号付き。クリック対象は「」で囲む）

### 注意・補足

- （業務ルール上の注意、エラー時の対処、関連画面へのリンク）
```

節が長くなるときは「操作手順」の後に `### <具体的な作業名>` の小見出しを足してよい（例: 第 6 章の「NE 連携 CSV でまとめて登録する」）。テンプレートを壊すのではなく、テンプレートの中に足す。

### 章の冒頭

各章はいきなり節に入らず、次を置く。読者が「この章は自分の業務のどこか」を判断できるようにするため。

1. 章で何をする画面かを 1〜2 文
2. 対応する業務フローへのリンク（`本章は [WF-1（自社出荷）](01-業務フロー.md#...) の出荷工程に対応します。`）
3. 「画面の開き方」（メニューと URL）
4. タブ一覧の表（タブ / 役割 / 節へのリンク）
5. 隣接画面との境界の補足（「便種判定そのものは受注管理で確認します」など）

タブ表の「節」列は章内アンカー（`[7.1](#71-出荷予定)`）にする。読者はタブ名で探すので、タブ表が章の目次を兼ねる。

## 表記規約

`00-はじめに.md` の表記規約に従う。実装ではなく読者の語彙で書くのが要点。

| 規約 | 例 |
|------|-----|
| 文体はですます調 | 「〜します」「〜してください」 |
| ボタン・タブ・入力項目・選択肢は「」で囲む | 「検索」をクリックします |
| 画面の場所はメニュー → タブの順 | メニュー「受注」→ タブ「入金確認」 |
| 画面項目には丸数字を振り、表で対応させる | ①②③…（キャプチャ側の赤枠と対応） |
| ステータスは画面の表示名で書く | 「引当済」（`ALLOCATED` ではなく） |
| 専門用語は初出で簡潔に補足し用語集へリンク | [用語集 §1](用語集.md#1-業務用語) |

避けること:

- テーブル名・カラム名・API パス・クラス名を本文に出す（読者は画面しか見ない）
- 「〜が可能です」の多用（「〜できます」で足りる）
- 実装都合の説明（「非同期で処理されるため」→「反映まで少し時間がかかります」）

業務ルールに関わる注意は本文に混ぜず「注意・補足」に集める。読者が操作中に読むのは手順、つまずいてから読むのが注意だから。根拠がある注意には該当 ADR や設計ドキュメントへリンクを張る。

## 画面キャプチャ

キャプチャは **Playwright で自動生成する。手作業で PNG を置いてはいけない** — 次回の再生成で上書きされ、UI 変更のたびに撮り漏れが出る。

```bash
cd apps/sms/frontend
npm run screenshots:manual   # docs/manual/assets/ へ PNG を出力
```

| 項目 | 内容 |
|------|------|
| 生成 spec | `apps/sms/frontend/e2e/manual/manual-screenshots.spec.ts` |
| 設定 | `apps/sms/frontend/playwright.manual.config.ts` |
| 配信 | 本番ビルド（`vite build`）を `vite preview` で配信 |
| データ | spec 内の `page.route` による API モック（バックエンド不要） |
| 命名 | `<章番号>-<英字スラッグ>[-連番].png`（例: `07-scheduled.png` / `04-payment-confirm-01.png`） |

### 本番ビルドで撮る理由

ヘッダーのテーマとバッジは `import.meta.env.MODE` で決まる（`src/lib/theme.ts`）。dev サーバで撮ると黄色ヘッダーと「⚠ 非本番環境（DEVELOPMENT）」バッジが写り込み、利用者が実際に見る画面と食い違う。一方で **本番環境そのものへは接続しない** — マニュアルは Git 管理下で公開されるため、実在の顧客名・住所・電話番号がリポジトリに残るのを避ける。見た目は本番ビルド、データはモックで揃える。

この理由から、既定の E2E（`npm run test:e2e`）はこの spec を `testIgnore` で除外している。dev サーバで動かすと非本番テーマの PNG で上書きしてしまうため、除外を外さないこと。

### 新しい画面のキャプチャを足す

`manual-screenshots.spec.ts` にテストを追加する。既存テストが雛形になる。

1. 必要な API を `page.route` でモックする（モックしないと取得エラーの赤帯が写り込む）
2. `loginAs()` などの既存ヘルパーでログインする
3. 目的の画面へ `page.goto` する
4. 主要要素の表示を `expect(...).toBeVisible()` で待つ（待たずに撮ると描画途中が写る）
5. `await capture(page, '<章番号>-<slug>.png')` で撮影する

テスト名は `'<ファイル名>（<画面の日本語名>）'` の形にそろえる（例: `'04-orders-list（受注一覧）'`）。失敗時にどのキャプチャが壊れたかが分かる。

### データの方針

- 実在の顧客名・住所・電話番号・メールアドレスは載せない。ダミー値を使う
- 代表的な 1 件以上のデータが表示された状態で撮る。空状態を説明する節では空状態も撮る
- フィーチャートグル（ADR-060）は本番既定＝無効で撮影される。トグル配下の機能を載せる節は、本番で有効化してから撮影・記載する（[トグル一覧](../development/feature_toggles.md)）

## 進め方

### 新しい章・節を書く

1. **対象画面を実際に確認する。** 実装（`apps/sms/frontend/src/pages/`）とユーザーストーリーを読み、タブ構成・項目・操作の流れを把握する。推測で書くと読者がその場で詰まる
2. **どの業務フロー（WF-1〜WF-6）のどのステップかを決める。** 第 1 章から参照される位置づけがないと、読者はその画面をいつ使うのか分からない
3. **節をテンプレートに沿って書く。** 章の冒頭（概要・WF リンク・タブ表）も忘れずに置く
4. **キャプチャを spec に足して生成する**（前節の手順）
5. **索引を更新する** — `docs/manual/index.md` の章表、`00-はじめに.md` の全体構成表、`mkdocs.yml` の nav（`manual/` 配下）。章を足したのに索引が古いと、読者はそのページに辿り着けない
6. **`operating-docs` の Markdown Lint を通す**

### UI 変更に追従する

1. 変更された画面を特定し、該当節の「画面の説明」の項目表・「操作手順」を実装と突き合わせる
2. `npm run screenshots:manual` でキャプチャを再生成する
3. 生成された PNG と本文の丸数字・項目表がずれていないか確認する（項目が増減していれば表も直す）
4. 画面が増減した場合はタブ表と `index.md` の章表も直す

### 公開する

```bash
npx gulp manual:build   # docs/manual → apps/www/manual へ HTML 出力
```

`apps/www` へのデプロイは `deploy:dev:www` 系のタスクが担う。マニュアルは `mkdocs` の設計ドキュメントサイトにも載るため、章を増減したら `mkdocs.yml` の nav も合わせる。

## トラブルシューティング章（付録 B）

付録 B だけは操作章と型が違う。症状から引く Q&A 形式で書く。

- 見出しは `### Q<節>-<連番>. <症状を読者の言葉で>`（例: `Q1-1. ログインできない（「ログイン ID またはパスワードが正しくありません。」）`）
- 画面に出るメッセージはそのまま引用する。読者はメッセージで検索する
- 「確認すること / 対処」の 2 列表が使いやすい
- **仕様であって不具合ではないもの**は、そう明記する。これが分からないと問い合わせが増える
- エラーメッセージ早見表の節を維持し、新しいメッセージを追加したら載せる

## 注意事項

- 執筆前に既存章を 1 つ通読する。テンプレートの解釈が揃う（第 6 章 商品管理が短くて型が見やすい）
- キャプチャの手動配置は禁止。必ず spec 経由で生成する
- 個人情報・トークン・社内 URL を本文にもキャプチャにも残さない
- 章を追加・削除したら `index.md` / `00-はじめに.md` / `mkdocs.yml` の 3 箇所を必ず揃える
- ユーザーの指示があるまでコミットしない
