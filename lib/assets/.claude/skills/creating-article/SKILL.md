# 技術記事の執筆

読者は「読んで理解する人」ではなく **「自分の手元で同じ手順を再現する人」** である。したがってこのスキルの中心は **記事とコードと実行結果の同期** にある。

3 つの原則:

1. **数値は実装を動かして得た値だけを載せる。** 憶測・暗算・記憶の値を載せない。
2. **同期は人の注意でなく機械で守る。** 転記コードの一致、出力の一致、件数の一致を検査ツールにし、CI で回す。
3. **自分の出来を信じない。** 担当の自己申告（変異テストの結果など）は、独立した確認で裏を取る。レビューは別の視点で行う。

`PROJECT.md` が本ファイルと食い違うときは `PROJECT.md` を正とする（`PROJECT.md` は更新で上書きされない）。

## 全体フロー

```text
0 既存の把握 → 1 計画（Bolt） → 2 骨子 → 3 Bolt ごとの実装と執筆 → 4 全体レビューと対応 → 5 公開
                                          └ 3 は章ごとに  実装(TDD) → 実測 → 執筆 → 検査 → 変異確認 → コミット
```

承認ゲート（人が決める）: 新規ファイル・構造の作成、外部ライブラリの導入、CI の変更、章構成の変更。AI-DLC に従い、計画を書いて承認を得てから 1 Bolt ずつ進める。

## 0. 既存の把握

- 既存の連載を **最低 1 本通読** し、章の型・粒度・体裁を揃える
- 規約ドキュメント・`PROJECT.md`・検査ツールの有無を確認する（ある規約が一次情報）
- 同じ題材の既存連載との **重複と差別化**（独立して読めること）を確認する

## 1. 計画（outline）

計画ドキュメント（`outline.md`）に次を書き、承認を得る。

- 読者・ゴール・前提（既存連載との関係）、章構成表（章・題材・実装する関数・図）
- 使う技術の導入順（NumPy・pandas などは、最初に使う章の前に承認を得る）
- **Unit と Bolt**: 依存の少ない単位に分け、最初の Bolt はウォーキングスケルトン（雛形 + 第 1 章）にする
- 承認事項の一覧と、決定の記録（採用しない案の理由も）
- 「次のステップ」: Bolt ごとの結果・判断・学びを、完了のたびに追記する（ガードレールの置き場）

## 2. 骨子

索引・読み方・章の目次・サイトのナビゲーション・記事トップの行・CI の対象。章は書けたぶんだけ足してよい。件数（章数・連載数）に依存する記述は、追加のたびに全箇所を更新する。

## 3. Bolt ごとの実装と執筆

### 章の型（読者の学習設計）

各章は同じ節構成にする（学習が定着する順）:

1. この章の地図（図を先に見せる。式とコードの対応表。前提）
2. 準備（実行コマンドと、期待する `N passed`）
3. **予想する** — 問いだけ。**答えを書かない**。手計算できる数値を章をまたいで使い回すと、予想の効果が高い
4. 考え方（理論・規則）
5. **プログラミング** — テスト → 失敗を確認（Red）→ 最小の実装（Green）→ 整える（Refactor）の小節。図。最後に小節 **「予想の答え合わせ」**（スクリプト 1 つ + 出力 1 つ + 説明。出力を実行して貼る）
6. 規則で言うと（混同注意の表。**このモデルが成り立たない場面**を具体的に書く）
7. 練習問題（想起・生成・多様・交互。解答は折りたたみで、実行できる）
8. 振り返り・まとめ（次章の予告。最終章は次に読む連載の案内）

分量は 1 章 600 行を目安にする。1 章に新しい構文・概念を詰め込まない（初学者向けは、新しい道具を 1 章 1〜2 個まで。導入は動かす例 → 出力 → 1 行ずつの解説）。記号は連載の記号表に載せ、章をまたいで衝突する文字（k・b・c・e など）は、衝突を注記するか文字を変える。

### 章のサイクル

1. **参照章を読む**（同じ連載の既存章）
2. **実装を TDD で作る** — テストを書き、**失敗を確認**し、最小限を実装。先回りしない。数値の境界（0、1、無限大、空、2 点だけ）と、小さい正の値（0 < x < 1）、許容誤差の効く点（超過量が 1e-6 など）のテストを書く。検証関数は章をまたいで共通化し、公開名にする
3. **実行して値を観察する** — 記事の数値はここで得る
4. **執筆** — テンプレートに `{{パス:名前}}` で実装・テストの原文を差し込み、ビルドスクリプトで記事を生成する（手で転記しない）。コードは必ずコードフェンスの中に置く
5. **機械検査** — 転記コードと実装の一致、出力の一致、`N passed` の一致、予想の答え合わせの実行、図の指紋
6. **独立した変異確認** — スクラッチの複製で演算子・境界を変異させ、テストが落ちることを確かめる。**担当の自己申告に頼らず、別に確かめる**（境界のテスト不足は、自己申告では見つからないことが多い）
7. **コミットを分ける** — 実装 / 記事 / CI

### 並列化

依存しない章は、複数エージェントで並列に進めてよい。ただし各担当に **担当ファイルを明示的に渡す**（プレースホルダを残さない）。担当の報告は、検査ツールと独立した確認で検証してから統合する。共有する資産（図の登録、共通パッケージ）は、競合しないように 1 か所で統合する。

## 4. 全体レビューと対応

連載の区切り（全章完成、または大きな部の完成）で、5 視点（プログラマー・テスター・アーキテクト・テクニカルライター・ユーザー代表）を **読み取り専用で並列** に走らせる。

- ユーザー代表には、**リポジトリを複製して実際に写経させる**（import・実行手順・補助関数の欠落は、ここでしか見つからない）
- 報告は `docs/review/<連載>_review_<日付>.md` に統合する（総合評価・改善提案を高/中/低・指摘元・矛盾事項・視点別の要約）。索引と `docs/log.md` を更新する
- 対応は **高から**。コードの修正は、テストを先に書き、Red を確認する。直したら記事の転記コードと件数を再同期し、全検査を通す
- 対応しない・後回しにする指摘は、**理由と共に** 報告書と outline に残す。ユーザーの承認なしに「対応済み」と書かない
- 人に直された振る舞いは、このスキルの原則・`PROJECT.md`・`CLAUDE.md` に反映して、繰り返さない

## 5. 公開

全検査（テスト・カバレッジ・lint・型・記事・答え合わせ・図・サイトのビルド）が通ってから push し、CI の成功まで確認する。**確認していないことを「通った」と書かない**（ローカルにないコマンドの実行結果を推測で報告しない）。

## 完了チェックリスト

- [ ] 計画・骨子・ナビゲーション・索引の件数が揃っている
- [ ] 各章に「予想する」（答えなし）と「予想の答え合わせ」がある
- [ ] 全テスト通過・カバレッジ 100%・lint・型クリーン
- [ ] 記事のコード・出力・件数の機械検査が OK
- [ ] 独立した変異確認を行い、生き残りは等価か、テスト追加済み
- [ ] 全体レビュー（5 視点）の報告書があり、高は対応済み、未対応は理由付き
- [ ] サイトのビルドが警告なし（実際に実行して確認）
- [ ] 実装・記事・CI を分けてコミットし、push 後の CI がグリーン

## 落とし穴（この連載の作業で実際に起きたこと）

- シェルのヒアドキュメントは `\n` を実際の改行に変える。複数行の Python は Write ツールで書く
- 担当エージェントの自己申告の変異テストは甘い。独立の演算子置換で、境界の不足が見つかった
- 浮動小数点: `isclose` に `abs_tol` がない、`.any()` で「すべて同じ」を判定する、行列式の絶対値で特異を判定する、は、いずれも誤判定の元
- 「0 より大きい」検査は、0 < x < 1 の有効値でテストしないと、`<= 1` への変異が生き残る
- 描画テストは、ヘッドレスのバックエンドに固定する（環境差でテストが不安定になる）
- 記事を直接編集すると、テンプレートとずれる。大きく直すときは、記事を正としてテンプレートを作り直す
- 変更の途中で件数（`N passed`）や転記コードがずれる。検査ツールを必ず再実行する
